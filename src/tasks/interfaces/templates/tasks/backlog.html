{% extends "base.html" %} {% block title %}Tasks · Budget Tracker{% endblock %} {% block content %} {# ONE top-level x-data scope owns everything interactive on this page: the Create Task button and its modal, the per-row Decompose buttons, the Edit and Delete buttons and their two modals, and the finished-task section. They share a scope deliberately rather than each row getting its own. The decompose buttons all mutate the same list, so a single `pending` map keyed by task id is what lets two buttons on two different rows show their own spinner without the page growing one scope per task. A second `x-data` inside this one is the bug AGENTS.md's Alpine rule warns about, so there is none. ## Why the edit modal reads its values from `dataset` The obvious way to build this is `@click="openEdit({name: '{{ task.name }}', ...})"` -- one modal, fed by a per-row JavaScript object literal. It is rejected, and not as a style preference: * `x-data`'s body is a JavaScript expression, so a task named `'); fetch(...)//` would execute. `tests/integration/web/test_security.py:: test_user_data_is_not_interpolated_into_javascript` exists to catch exactly this, and interpolating task fields would fail it -- correctly. * Even inside a quoted attribute it would need JS-level escaping, and Jinja's HTML escaping is not JS escaping. They differ on quotes, backslashes, and newlines, which a markdown description is full of. So the row's values travel as HTML attributes on the Edit button, escaped by Jinja the way every other attribute on this page is, and `openEdit($el)` reads them back off `$el.dataset`. The same mechanism `x-init` already uses for the CSRF token and the decompose URL. The trade is that a multi-line description occupies a multi-line attribute -- ugly, harmless, and correct. The descriptions are rendered by `gFm.render`, which is the page's Markdown surface. Nothing here is interpolated into `x-html` unsanitised -- see `_markdown.html` for why DOMPurify is not optional. #}
